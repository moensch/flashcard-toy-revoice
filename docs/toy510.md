# The 510-word version

Notes on the bigger sibling (USB-C charging). Same idea as our 224-word toy; the
differences:

| | 224-word toy | 510-word toy |
|---|---|---|
| Flash | SY25Q40P (Puya P25Q40H), 512 KB, ID `85 60 13` | UC25HQ80, 1 MB, ID `b3 60 14` |
| Card *N* plays | `NNN.f1a` | `(1000+N).f1a`, e.g. card 1 → `1001.f1a` |
| Prompts | `1501`–`1515` | `3006`–`3014` (4 short beeps, 5 spoken) |
| Card code | 8 bits, 2/4 swapped | 9 bits, plain order (see [barcode.md](barcode.md)) |
| Card size | 59 x 88 mm | 60 x 90 mm |
| In-circuit read/write | unreliable, chip had to come off | **works** through the clip |

Word list with numbers: [`data/cards510.csv`](../data/cards510.csv). Its `old_number`
column links words that also exist in the 224-word set (`data/cards.csv`), so one
recording can serve both toys (`=69` means "same sound as card 69").

## What we found

- **Filesystem:** the same JieLi format as in [filesystem.md](filesystem.md): 499
  files (`1001`–`1490` plus the prompts), all checksums OK, the chip nearly full
  (2.4 KB free). The directory ends right where the data starts, so adding an entry
  means moving the first file (we moved the 310-byte beep `3006`).
- **Cards 491–510 have no file** (the last 20 adjectives), yet the toy plays them.
  Their sounds must be in the MCU's own memory. Adding a `1491.f1a` to the flash
  changed nothing: card 491 still played the built-in "bright". These 20 can't be
  revoiced through the flash.
- **Shared sounds work:** we pointed card 400 ("rice") at card 69's identical "rice"
  data, which freed 2 KB.
- **In-circuit:** with the batteries out and the Pico powering the board, reads came
  back with 0% dropped bits, and a 3-sector write verified on the first read.
- **The reader** has 9 IR sensors and a card-present microswitch in the middle (code
  position 5); code position 0 has no sensor. So 511 is the highest possible code.

## Tool status

The tools in `tools/` still assume the 512 KB chip (`SIZE` in `common.py`,
`JEDEC_ID` in `pico/spi.py`, `DIR_END` in `write_flash.py`). The Pico's own
filesystem can't hold a 1 MB dump in one go; dump in two 512 KB halves.
